# إصلاح بطء التبديل وتشخيص رفض HTML — 1.3.1

يتبع هذا الإصلاح تكامل Premium في Issue #2 وPR #3. لا يغيّر هوية جهاز الاشتراك أو ملفات المستخدم أو ترتيب الطابور أو مخطط قاعدة البيانات.

## ما تغيّر

- تذكّر فهرس آخر بوابة HTTPS نجحت في ملف Premium الخاص بـroot، وإعادة استخدامها أولًا في الطلب التالي وعقب إعادة تشغيل الخدمة. تبقى البوابات المعتمدة الأخرى بدائل محدودة. لا تقبل الخدمة عنوان بوابة من المتصفح أو من استجابة الشبكة.
- حل اسم Shodan مرة واحدة وإعادة استخدام العناوين المحلولة في اتصال TCP، ثم تنفيذ اختبار TLS إلى Shodan واختبار عنوان الخروج بالتوازي، ضمن مهلة العملية الأصلية. تبقى الشهادات والتحقق من Handshake والمسارات وحماية التسرب مطلوبة.
- عند إطلاق العامل مباشرة بعد التحقق، يمكن استخدام فحص عمره أقل من عشر ثوانٍ للنفق نفسه، مع إعادة التحقق الفعلي من الواجهة والمسار والجدار الناري. قطع النفق يمسح الفحص؛ الفحص القديم أو غير السليم يُعاد بالكامل.
- لا يجري المراقب اختبارًا إضافيًا إذا تم التحقق مؤخرًا. تُعاد أزمنة إعداد الاتصال والواجهة والتحقق في استجابة الاتصال لتسهيل التشخيص.
- تشخيص الشبكة الصريح يرسل طلبًا واحدًا إلى الصفحة الرئيسية لـShodan ويفحص حالة HTTP والترويسات فقط. يوضح رفض الوصول أو تحدّي المتصفح بشكل مستقل عن سلامة النفق. فحوص المراقبة والتحقق التلقائي لا ترسل طلبات صفحات Shodan.
- يميّز العامل رد `cf-mitigated: challenge`، ويوقف جمع HTML عند رفضه مع حفظ Checkpoint، دون اعتباره عطل VPN أو نتيجة بحث فارغة. تبقى المهمة على HTML عند فتح الاستكمال.

## سبب فشل الاستعلام الحالي

آخر مهمة HTML كانت متوقفة بسبب HTTP 403، بينما نجح تحقق النفق وعنوان الخروج. أكّد اختبار مباشر محدود من العامل المعزول أن الصفحة الرئيسية أعادت HTTP 403 مع `cf-mitigated: challenge`. توضح [وثائق Cloudflare الرسمية](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/) أن هذه الترويسة تدل على صفحة تحقق.

اشتراك Amnezia يؤمن اتصال VPN؛ لا يمنح صلاحيات بحث Shodan ولا يحل تحقق المتصفح. لا يتضمن عميل HTML الحالي جلسة متصفح تفاعلية. لا يكفي نجاح VPN أو فتح الموقع على جهاز آخر لضمان قبول طلب العامل. يحتاج جمع HTML إلى أن يقبل Shodan الطلب من هذا العميل؛ هذا قيد وصول خارجي، ولم يُدّع نجاح استعلام حي عند وجوده. لا يحتاج هذا الإصلاح مفتاح API ولا يبدّل وضع المهمة إلى API.

## التثبيت والتراجع

تُطبّق خطوات النسخ الاحتياطي ونشر إصدار مستقل في [دليل النشر](VPN_DEPLOYMENT_AR.md). لا توجد Migration جديدة. يجب خلو الطابور من أعمال قيد التشغيل قبل إعادة تشغيل التطبيق والخدمة المساعدة. يُحفظ ملف `premium.json` الخاص بهوية العامل وأسراره بصلاحيات root فقط.

سجل النشر المرفق يحدد الإصدار السابق والنسخة الاحتياطية. للتراجع عن الكود: أوقف خدمتي التطبيق والمساعد، أعد الرابط `/opt/shodan-studio/current` إلى `previous_release` المسجل، ثم شغّل المساعد والتطبيق وأعد الاتصال بملف العامل السابق من اللوحة. يبقى مخطط البيانات متوافقًا. لا تستعد قاعدة البيانات القديمة فوق نتائج أحدث إلا ضمن إجراء استعادة مقصود.

نُشرت النسخة النهائية في `/opt/shodan-studio/releases/release-C094WAMQ`. جرت القياسات من API اللوحة بالمصادقة وCSRF، مع فحص SSH واللوحة أثناء التبديل:

|---|---:|

| من رومانيا إلى ألمانيا | 10.847 ثوانٍ |

القياس السابق المسجل لرومانيا كان 28.718 ثانية، مع محاولة فاشلة أخرى بلغت 55.910 ثانية. هذه عينات فعلية في أوقات مختلفة، وليست ضمانًا ثابتًا للزمن أو تجربة مقارنة تحت ظروف شبكة متطابقة. انخفض إعداد Premium في القياسات النهائية إلى 1.5–2.2 ثانية بعد تذكّر البوابة.

أثناء الجولة الأولى قبل تحسين DNS، فشلت محاولة رجوع إلى رومانيا في Handshake. نجحت الاستعادة اللاحقة وأعيد الملف الأصلي. احتُفظ بالفشل في `performance-live.json`؛ لا يلغيه نجاح الجولة النهائية في `performance-final-live.json`. لا يزال زمن الاتصال ونجاح النفق يتأثران بالشبكة وخادم الخروج.

أعاد طلب HTML محدود للاستعلام الموجود `HTTP_403` و`BROWSER_CHALLENGE`، دون تعديل المهمة أو نتائجها (`performance-html-live.json`). وفي فحص الصفحة الرئيسية النهائي انتهى HTTP بمهلة رغم نجاح DNS/TCP/TLS والنفق؛ ظهر `source_access=check_failed` بدل ادعاء صلاحية البحث. لم تنجح عملية بحث Shodan حيّة في هذه الاختبارات.
